# AGENTS.md

## Repository Overview

**terraform-provider-rubrik** is the Terraform provider for Rubrik Security Cloud (RSC). It exposes the
RSC GraphQL API, through the Go SDK, as Terraform resources, data sources, and list resources.

- **Module:** `github.com/rubrikinc/terraform-provider-rubrik`
- **Registry address:** `registry.terraform.io/rubrikinc/rubrik`, resource prefix `rubrik_`
- **Go version:** 1.26+
- **SDK:** `github.com/rubrikinc/rubrik-polaris-sdk-for-go`
- **Main branch:** `main`

## Key Directories

| Path | Description |

| `internal/provider/` | All provider code: resources, data sources, list resources, tests |

## Skills

Skills load on demand, so long checklists and templates live there instead of in this file. They are in
`.agents/skills/`, and `.claude/skills/<name>` is a symlink to each one for Claude Code. Invoke a skill with `/<name>` in
Claude Code or `/skill:<name>` in pi. Both tools also load one automatically when the task matches its description. Edit
the files under `.agents/skills/`, and add a symlink in `.claude/skills/` for every new skill.
## Provider Frameworks

SDKv2 and the Terraform Plugin Framework are muxed together. **All new resources, data sources, list resources, and
actions MUST use the Framework** (`framework_*.go`). Never create new `resource_*.go` or `data_source_*.go` files.
SDKv2 files only get bug fixes in place, or are converted with the `migrate-to-framework` skill.

Types that existed in the `polaris` provider are registered twice, `newXxx` for `rubrik_` and `newPolarisXxx` for the
deprecated `polaris_` alias, and carry a `_move.go` that moves state from the `polaris_` type. Brand-new types have
neither. The `polaris` provider is deprecated in favour of this one; never add new types there.

## New Types

Use the `new-provider-type` skill (arguments: `<kind> <name>`) to scaffold a resource, data source, list resource, or
action. It covers file
layout, registration, identity and import, examples, the changelog entry, and the test skeleton. Every new resource
implements resource identity and import, and gets a list resource when RSC has a list API for it.

## Code Rules

- MIT license header on every Go file (copyright Rubrik, Inc.). Copy it from an adjacent file
- Doc comments on all exported identifiers, and on any other function whose contract is not obvious
- Schema field names come from `names.go`, never string literals. Check the constant does not exist before adding it
- Wrap description constants in `description()`. It renders the description as a Go `text/template` and converts acute
  accents to backticks, since raw string literals cannot contain backticks. A literal `{{` must be written
  `{{"{{"}}`, or the schema panics when built. Shared snippets live in `snippets.go`
- Start every Framework method with `tflog.Trace(ctx, "<receiver type>.<Method>")`
- Get the RSC client with `r.client.polaris()` and report failures as `RSC client error`. Call the SDK through its
  wrappers, e.g. `access.Wrap(client).SomeMethod(ctx, ...)`
- Handle `graphql.ErrNotFound` with `errors.Is`: Read removes the resource from state, Delete ignores it
- Use typed regions (`aws.Region`, `azure.Region`, `gcp.Region`) from the SDK, never `string`
- Use `github.com/google/uuid` for UUIDs. No custom parsing or formatting
- Mark credentials `Sensitive: true`. Use `WriteOnly: true` for values RSC needs on create or update but never returns
- Read adjacent code before editing and follow its patterns
- Inject dependencies for testability. Prefer fakes over mocks

### Helper Functions

Do not add a function for logic used fewer than four times. Inline it. One or two call sites is indirection, and three
is borderline and usually still better inline. At four or more call sites a helper is justified. Name it for the
feature (`gcpBigQueryPlannedBlockCount`, not `getCount`) and keep it next to its callers. Required interface methods
(`Schema`, `Read`, ...) are not helpers. The same rule applies to test code. The one exception is logic extracted so it
can be unit-tested on its own, such as plan-time validation that needs no client.

## Testing

- **Names:** CamelCase, no underscores. Acceptance tests are `TestAcc<Name>Resource`, `TestAcc<Name>DataSource`,
  `TestAcc<Name>ListResource`, and `TestAcc<Name>Action`. Unit tests are `Test<Thing>`
- **Prefixes matter:** CI and the `Makefile` select tests by name. Cloud-specific acceptance tests must start with
  `TestAccAws`, `TestAccAzure`, or `TestAccGcp` (or the `Polaris` variants), and tests behind the `cdm` build tag with
  `TestAccCDM`. A test that does not follow this runs in the wrong CI stage
- **Unit tests** need no RSC and no `TF_ACC`. Use them for conversion, validation, and plan-time logic. Make them
  table-driven with `t.Run`. Do not test the framework or trivial conversions
- **Acceptance tests** use `resource.Test` (not `ParallelTest`) with `ProtoV6ProviderFactories`. Comment every step with
  what it verifies. Assert with `ConfigStateChecks`, `statecheck`, `knownvalue`, and `tfjsonpath`, not
  `TestCheckResourceAttr`. Every resource has a `CheckDestroy`, see `framework_checkdestroys_test.go`
- **Import is always tested** for resources: `ImportCommandWithID` with `ImportStateVerify`, then `ImportBlockWithID`
  and `ImportBlockWithResourceIdentity`, each with `plancheck.ExpectEmptyPlan()`. Every `ImportStateVerifyIgnore` entry
  needs a comment saying why. Resources with identity also assert `ExpectIdentity` and `ExpectIdentityValueMatchesState`
- **List resources** are tested with `Query: true`, `querycheck.ExpectIdentity`, and
  `tfversion.SkipBelow(tfversion.Version1_14_0)`
- **Gating:** use `skipUnlessAcceptanceTest(t)` in helpers that call RSC, and `skipUnlessFeatureEnabled(t, flag)` for
  anything behind an RSC feature flag
- **Environment:** `TF_ACC=1`, credentials in `RUBRIK_SERVICEACCOUNT_FILE`, and for cloud tests `TEST_AWSACCOUNT_FILE`,
  `TEST_AZURESUBSCRIPTION_FILE`, `TEST_GCPPROJECT_FILE`, and `TEST_RSCCONFIG_FILE`
- **CDM** (Data Center) tests are behind the `cdm` build tag and need `TEST_DATACENTER_FILE`. `-tags=cdm` adds them to
  the default suite, it does not replace it
- **Run one type:** `TF_ACC=1 go test -count=1 -timeout=120m -run '^TestAccCustomRoleResource$' -v ./internal/provider`

## Documentation

**Never manually edit files in `docs/`.** Run `go generate ./...` and commit the result.

- Templates in `templates/` are the source of truth when they exist. Otherwise docs come from code descriptions, schema
  definitions, and `examples/`
- Callouts: notes use `->`, warnings use `~>`, critical notes use `!>`
- Do not use backticks inside markdown link text: `[rubrik_foo docs](../resources/foo.md)`, not
  `` [`rubrik_foo` docs](...) ``
- Changelog: `templates/guides/changelog.md.tmpl`. Upgrade guides: `templates/guides/upgrade_guide_v<VERSION>.md.tmpl`

### Changelog Entry Format (ordered by priority)

1. Breaking changes: `* **Breaking Change:** [description]. [link to upgrade guide].`
2. Deprecations: `* **Deprecated:** [field] in [resource]. Use [replacement].`
3. New resources: `* New resource added for [name] which [description]. [[docs](link)]`
4. New data sources: `* New data source added for [name] which [description]. [[docs](link)]`
5. Features: `* Add support for [feature] in [resource]. [[docs](link)]`
6. Improvements: `* Improve [what] in [resource].`
7. Bug fixes: `* Fix a bug in [resource] where [description].`

## Pre-Commit Checklist

This mirrors CI. The `tf-checks` skill runs all of it.

1. `go mod tidy` leaves `go.mod` and `go.sum` unchanged
2. `gofmt -l .` prints nothing
3. `go vet -tags=cdm ./...`
4. `staticcheck -tags=cdm ./...` (v0.7.0)
5. `go generate ./...` leaves no diff
6. `go test ./...`

## Commit Messages

Follow the seven rules of a great Git commit message (https://cbea.ms/git-commit). Key points: subject line ≤50 chars,
imperative mood, no trailing period. Use a body only when the WHY is non-obvious from the diff — not to list every file
changed.

## Pull Requests

Read `.github/pull_request_template.md` before creating a PR and fill it in faithfully. If how the change was tested
isn't clear from context, ask. Don't remove unchecked checkboxes. Don't hard-wrap prose — write paragraphs as single
lines and let GitHub handle wrapping.

## Go SDK Dependency

```bash
go get github.com/rubrikinc/rubrik-polaris-sdk-for-go@<version>
go mod tidy
```

During development a commit-based pseudo-version in `go.mod` is fine. Before a release the SDK must be pinned to a
semver tag. Find the SDK source with `go list -m -json github.com/rubrikinc/rubrik-polaris-sdk-for-go | jq -r .Dir`,
which respects `GOWORK`. Do not read the module cache directly. **Never add `replace` directives** to `go.mod`; use a
`go.work` file to work against a local SDK.

## Release Process

1. Pin the SDK to a semver tag (tag the SDK first, then update `go.mod`)
2. Run the pre-commit checklist
3. Update `templates/guides/changelog.md.tmpl` with all changes since the last release. For breaking changes, new
   features, or deprecations, create or update `templates/guides/upgrade_guide_v<VERSION>.md.tmpl`. Run
   `go generate ./...`, then commit, push, and merge via PR
4. Tag and release from an up-to-date `main`:

```bash
git tag v<MAJOR>.<MINOR>.<PATCH>
git push --dry-run --tags   # verify first
git push --tags             # triggers the GitHub Actions release (GoReleaser, GPG signing, Terraform Registry)
```

Versioning is SemVer. **Major** is for large refactors or breaking changes. **Minor** is for new features and may
include small breaking changes with an upgrade guide. **Patch** is for backward-compatible bug fixes.
