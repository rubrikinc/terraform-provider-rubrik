# Upgrade Guide v1.12.0

## Before Upgrading

Review the [changelog](changelog.md) to understand what has changed and what might cause an issue when upgrading the
provider.

~> **Note:** If you are upgrading across multiple minor versions, review the upgrade guide for each intermediate version
as well. Each guide documents breaking changes and migration steps specific to that release.

## How to Upgrade

Make sure that the `version` field is configured in a way which allows Terraform to upgrade to the v1.12.0 release. One
way of doing this is by using the pessimistic constraint operator `~>`, which allows Terraform to upgrade to the latest
release within the same minor version:
```terraform
terraform {
  required_providers {
    rubrik = {
      source  = "rubrikinc/rubrik"
      version = "~> 1.12.0"
    }
  }
}
```
Then upgrade the provider by running:
```shell
% terraform init -upgrade
```
Validate the configuration:
```shell
% terraform plan
```
If you get an error or an unwanted diff, please see the _Significant Changes_ section below for additional
instructions. Otherwise, refresh the state to the v1.12.0 version:
```shell
% terraform apply -refresh-only
```

## Significant Changes

### `CLOUD_COST_REPORT` can be declared on AWS IAM roles accounts

The `CLOUD_COST_REPORT` feature grants RSC the permissions to read the AWS Cost and Usage Report of an account, from
which the RSC Cloud Cost Report is built. It is accepted by the `feature` block of the `rubrik_aws_cnp_account`
resource, the `features` field of the `rubrik_aws_cnp_account_attachments` resource, and the `rubrik_aws_cnp_artifacts`,
`rubrik_aws_cnp_permissions` and `rubrik_aws_permission_groups` data sources. Its only permission group is `BASIC`.

RSC enables the feature on its own for any account carrying a feature which accrues AWS spend, and it never removes it
along with those features. The v1.10.0 release stopped tracking the feature for that reason. This release keeps that
behaviour for configurations which do not declare the feature: an undeclared cost report is left to RSC, does not show
up in state or in a plan, and is still removed when the account is destroyed. Nothing changes for such configurations.

Declaring the feature is how an account onboarded with IAM roles grants the permissions cost reporting needs. RSC adds
the feature in the `MISSING_PERMISSIONS` state when it enables it on its own, and it stays in that state until a role
carrying the `CloudCostReportPolicy` policy is registered. To grant the permissions, add the feature to the
`rubrik_aws_cnp_account` resource and to the data sources the roles are built from:
```terraform
resource "rubrik_aws_cnp_account" "account" {
  name      = "My Account"
  native_id = "123456789123"
  regions   = ["us-east-2"]

  feature {
    name              = "CLOUD_NATIVE_PROTECTION"
    permission_groups = ["BASIC"]
  }

  feature {
    name              = "CLOUD_COST_REPORT"
    permission_groups = ["BASIC"]
  }
}
```
Once declared, the feature is tracked like any other feature. It cannot be removed from the configuration while
`CLOUD_NATIVE_ARCHIVAL`, `CLOUD_NATIVE_DYNAMODB_PROTECTION`, `CLOUD_NATIVE_PROTECTION`, `CLOUD_NATIVE_S3_PROTECTION`,
`EXOCOMPUTE` or `RDS_PROTECTION` remain declared, since RSC refuses to disable cost reporting while a feature which
accrues AWS spend is enabled. Removing it from the configuration while none of them remain removes the feature from
the account. Note that RSC leaves the Cost and Usage Report definition and the S3 bucket it writes to in the AWS account
when cost reporting is removed.

Declaring the feature requires cost reporting to be enabled for the RSC account. When it is not, RSC rejects the
onboarding with an error similar to:
```text
Error: Failed to add AWS account: failed to add account: Cloud Cost Report feature passed but AWS Cloud Cost Report is not enabled.
```

The feature is not imported along with an account, and it is not part of the configuration generated by the
`rubrik_aws_cnp_account` and `rubrik_aws_cnp_account_attachments` list resources, since neither can tell a cost report
the account was configured with from one RSC enabled on its own. Add it to the configuration after importing if the
account should track it.

### `rubrik_aws_cnp_permissions` returns the cost report policy

RSC decides whether the cost report policy applies to a request from the requested features, and it ignored features
specified with permission groups when doing so. The provider now names the requested features in a way which RSC
accepts, so the `CloudCostReportPolicy` policy is returned when `CLOUD_COST_REPORT` is requested.

The same change means RSC can add `CLOUD_COST_REPORT` to a requested feature set on its own, the same way it adds
`CLOUDACCOUNTS`, when cost reporting is enabled for the RSC account and a requested feature accrues AWS spend. Expect a
one-time change in the `customer_managed_policies` of the data source on such RSC accounts, adding the
`CloudCostReportPolicy` policy for a feature set which does not name the feature. The policy is the one RSC is waiting
for on the account, so applying the change grants the permissions RSC asked for, and the `MISSING_PERMISSIONS` state
of the feature clears once the roles are registered with the `rubrik_aws_cnp_account_attachments` resource.

### `rubrik_aws_account` removes cost reporting on destroy

Destroying a `rubrik_aws_account` resource now removes the `CLOUD_COST_REPORT` feature when RSC has enabled it on the
account. RSC removes an account once its last feature is removed, but it never removes cost reporting along with the
features it was enabled for, so destroying the resource could leave the feature, and with it the account, behind in
RSC. The feature cannot be declared in the resource, as RSC adds it to the CloudFormation stack on its own.
